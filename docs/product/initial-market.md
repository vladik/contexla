# Initial market wedge

## Team and go-to-market constraints

Contexla begins with a small CMS-focused agency led primarily by an architect
and developer. Sales capacity is limited to direct relationships, the agency
website, LinkedIn, demonstrations, and project opportunities.

The first offering therefore must:

- solve a problem organizations already recognize and fund;
- fit existing Sitecore, Drupal, migration, and architecture credibility;
- be deliverable by one primary developer;
- produce visible, reusable evidence rather than depend on a long platform
  build;
- create consulting revenue before requiring a mature self-service SaaS motion.

## Recommended first Application: Digital Estate Assessment

Digital Estate Assessment answers:

> What is actually in this digital-content estate, how is it connected, what is
> used, and what creates cost or migration risk?

Potential assessment areas include:

- CMS versions, modules, packages, and custom code;
- sites, content types, fields, components, and content volumes;
- workflows, roles, scheduled jobs, and publishing configuration;
- integrations, endpoints, webhooks, search, DAM, analytics, and identity;
- infrastructure and deployment topology;
- content and asset usage;
- accessibility or operational risk indicators;
- modernization, retirement, and migration recommendations.

This is a better first commercial wedge than a universal Web History product
because it matches observed Canadian demand: organizations are evaluating
Sitecore exits, lower-cost alternatives such as Drupal, and existing Drupal
estates whose scope is poorly understood.

## Smallest sellable version

The first version should not promise automatic discovery of every system.
Instead, it can combine:

1. a structured engagement template;
2. a read-only Drupal snapshot collector or documented export procedure;
3. uploaded architecture and configuration evidence;
4. deterministic inventory and rule-based findings;
5. an evidence-backed HTML/JSON report;
6. architect review and recommendations.

The product can reduce collection and analysis time while expert judgment keeps
the deliverable credible. Later versions can add live connections, more CMSs,
continuous monitoring, and agent-assisted investigation.

## Validation before substantial build

Validate these questions with prospects and recent project evidence:

- Who owns the problem and signs for the work?
- What event triggers an assessment: renewal, migration, acquisition, audit, or
  cost reduction?
- Which outputs are valuable enough to fund?
- What evidence can customers safely provide?
- Must the software run inside their network?
- Is the buyer paying for a one-time assessment, repeat monitoring, the software,
  or a combined service?
- Which findings change a budget or migration decision?

The strongest proof is a paid assessment delivered with the narrow product, not
general interest in the platform vision.

## Early integration strategy

Begin with the lowest-risk collection mode that supports a real assessment:

- uploaded snapshot or export;
- a read-only collector run by the customer;
- a standard API using encrypted credentials;
- only then, a CMS-installed Connector when native access or event capture is
  genuinely necessary.

This keeps onboarding feasible for enterprise environments and prevents the
first release from being blocked by plugin approval or deep CMS support.
