# Initial market wedge

## Team and go-to-market constraints

Contexla begins with a small CMS-focused agency led primarily by an architect
and developer. Sales capacity is limited to direct relationships, the agency
website, LinkedIn, demonstrations, and project opportunities.

The first offering therefore must:

- solve a problem organizations already recognize and fund;
- fit existing Sitecore, Drupal, migration, and architecture credibility;
- be deliverable by one primary developer;
- produce visible, reusable evidence rather than depend on a long platform
  build;
- create consulting revenue before requiring a mature self-service SaaS motion.

## Current first portfolio hypothesis: Content Integrity Monitor

Content Integrity Monitor answers:

> Did important content facts reach every required representation correctly,
> and where are they missing, stale, or inconsistent?

Potential scenarios include:

- CMS delivery API versus rendered website;
- CMS or ERP facts versus search index values;
- content drift across delivery instances or regions;
- missing or stale downstream representations after a source change;
- important values exposed through JSON/CSV, APIs, and webpages.

This hypothesis is a better first portfolio proof than extending Digital Estate
Assessment because it produces an operational result, supports recurring Runs,
is demonstrable without customer-confidential evidence, and is adjacent to CMS,
integration, search, migration, and delivery work. Buyer demand remains to be
validated; this is not a settled market claim.

## Smallest demonstrable version

The first version should not promise arbitrary system discovery or universal
semantic comparison. It should combine:

1. authoritative JSON or CSV;
2. configured entities and important facts;
3. HTTP JSON and HTML representations;
4. deterministic extraction and normalization;
5. equality, missing, stale, and unavailable comparisons;
6. evidence-backed Findings and Run history;
7. a concise report and notification boundary.

The first proof explicitly excludes correction, synchronization, AI extraction,
PDF/OCR, accessibility certification, and a catalog of vendor-specific
integrations.

## Validation before substantial expansion

Validate these questions with prospects and recent project evidence:

- Which facts are duplicated and what does inconsistency cost?
- Which source is authoritative, and can that authority be stated explicitly?
- Which downstream representations fail or lag in practice?
- Who owns the problem and who responds to a Finding?
- Which inputs can customers expose through APIs, snapshots, or public pages?
- Must the software run inside their network?
- Is the buyer paying for a pilot, integration, ongoing monitoring, support, or
  software?

The strongest proof is a paid pilot or related project. Before that exists, a
complete synthetic demonstration and specific buyer response are valid reasons
for a bounded initial build. General interest in the platform vision is not.

## Early integration strategy

Begin with the lowest-risk acquisition modes that support the proof:

- uploaded JSON or CSV;
- public or synthetic HTTP JSON and HTML;
- a standard API using encrypted credentials;
- only then, vendor-specific Clients or a native Connector when access or event
  capture genuinely requires one.

This keeps onboarding feasible for enterprise environments and prevents the
first release from being blocked by plugin approval or deep CMS support.

## Initial operating model

Present a recognizable integrity problem and working demonstration first, then
explain Contexla as the repeatable monitoring and evidence foundation. Offer a
curated agency-operated or customer-hosted deployment according to data and
policy constraints. The Application detects, records, and notifies; it does not
silently repair or synchronize customer content.

Content Integrity should create responsible opportunities in integration,
search, CMS delivery, migration verification, deployment, support, and ongoing
operation while remaining useful by itself.

Do not fork the product per customer. Package differences as configuration,
Application Instances, Connections, Bindings, or versioned extensions that can
be evaluated for later reuse.
