# Digital Estate Assessment v1

## Product outcome

Digital Estate Assessment v1 turns approved evidence from one bounded CMS
estate into a traceable inventory, a set of deterministic findings, and an
architect-reviewed report that supports a modernization decision.

The first version is a service-supported Application, not a self-service
universal scanner.

## Primary user

The primary working user is the architect or technical lead conducting the
assessment. The report serves digital leadership, CMS owners, program managers,
and procurement or delivery teams.

## First supported path

```text
Customer or assessor prepares approved evidence
              -> evidence package upload
              -> package validation and hashing
              -> Drupal source Adapter
              -> normalized estate snapshot
              -> versioned Capability contracts and bound Processors
              -> deterministic assessment rules
              -> findings linked to evidence
              -> architect review
              -> HTML and JSON report
```

The first implementation may use a hand-prepared package or fixture. A customer-
run Drupal collector can be introduced only after a pilot confirms which data
is repeatedly valuable.

## Required v1 workflow

1. Create an Assessment with its decision, scope, and exclusions.
2. Add one or more Targets, beginning with a Drupal installation.
3. Upload an evidence package that conforms to the v1 contract.
4. Validate the package structure, hashes, source type, and collection metadata.
5. Run the Drupal Adapter to create a normalized snapshot.
6. Invoke required Capability contracts through their approved Processors.
7. Inspect the inventory and evidence gaps.
8. Execute deterministic assessment rules.
9. Review, annotate, accept, suppress, or revise findings without changing the
   original evidence.
10. Add expert findings that are explicitly distinguished from rule findings.
11. Generate an evidence-linked report and machine-readable export.
12. Run the assessment again later while retaining the prior snapshot and
    findings.

## Minimum inventory

Within the evidence made available, v1 should represent:

- installations and environments;
- sites and hostnames;
- CMS and runtime versions;
- modules/packages, including custom/contributed/core classification;
- content types and field summaries;
- themes/components when available;
- integrations and their direction, owner, and criticality when declared;
- infrastructure services when declared;
- source repositories or custom-code packages when declared;
- evidence gaps and unknown values.

Unknown is a valid, important value. The system must not infer absence merely
because an item was not present in collected evidence.

## Initial deterministic findings

The first rules should rely only on explicit evidence and configurable policy:

- required scope metadata is missing;
- an environment, integration, or custom module has no declared owner;
- a version or dependency is unknown;
- a custom extension lacks a repository or maintenance status;
- an integration lacks direction, authentication classification, or criticality;
- expected evidence was not collected;
- duplicate identifiers or conflicting inventory values exist;
- a declared lifecycle date violates the assessment policy;
- two comparable environment snapshots differ in selected configuration areas.

External lifecycle or vulnerability claims require a versioned, cited data
source. They must not be hard-coded from developer memory or generated by AI.

## Human review

The architect can:

- correct normalized metadata while preserving the original value;
- link additional evidence;
- record a rationale and confidence;
- change disposition or impact with an audit entry;
- mark a rule finding accepted, not applicable, duplicate, or needs
  investigation;
- add expert observations that clearly identify their author.

## Explicitly deferred

- automatic discovery of every integration;
- production credentials and live continuous scanning;
- autonomous migration estimates;
- security or accessibility certification;
- target-CMS selection;
- general workflow composition UI;
- agent-created production code;
- multiple CMS Adapters before the first Drupal path produces useful output;
- multitenancy and organization workspaces.

## Product proof

V1 succeeds when it supports a real assessment decision and the customer agrees
that its inventory, evidence gaps, and findings are more defensible or efficient
than the current spreadsheet/interview process. Completing the screens alone is
not success.

## Implementation status

The current fixture-backed slice implements steps 1–12 and produces an initial
HTML/JSON report. The HTML report presents the decision and scope, run method,
collection limitations, inventory, snapshot comparison, findings with
provenance, review history, and evidence appendix. It persists Application-owned
Runs, Evidence Items, Snapshots,
Inventory Items, Relationships, deterministic and attributed expert Findings,
append-only review decisions, and deterministic comparisons between consecutive
Snapshots. Normalized-value correction history and richer report sections
remain to be implemented after testing the slice with real college evidence.
